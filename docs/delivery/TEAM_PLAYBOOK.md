# HB-Lims 2–3人团队开发手册

依据[FRAMEWORK-V1](../standards/FRAMEWORK_BASELINE.md)。Owner认可规划；QA批准与软件实现未完成。核心方法：**模块化单体、合同先行、纵向小增量、短分支、每周集成、证据随代码交付**。

## 1. 工作模式和职责

| 人员/角色 | 主要责任 | 不可以替代的职责 |
| --- | --- | --- |
| 研发A/技术负责人 | FastAPI、PG模型/迁移、身份/状态/事务/审计、接口合同与关键评审 | 不代QA批准预期用途，不代检验员签名 |
| 研发B/前端负责人 | Next/AntD、V3.1主题、业务交互、生成客户端、组件和浏览器测试 | 不把页面禁用按钮当最终授权 |
| 研发C（有第三人时） | 仪器/企业集成、自动化测试、恢复/部署和联合回归 | 不独占所有测试责任，其他开发仍为自己的代码写测试 |
| QC业务负责人 | 样例、标准/方法/公式、异常规则、每周业务反馈 | 不以演示认可代替QA正式批准 |
| QA/验证负责人 | 适用性、风险、验证策略、独立审阅与最终质量批准 | 不把供应商报告视为责任转移 |
| IT/外部验证/厂家技术人员 | 按约定提供环境、协议适配、验证设计或实现支持 | 开发与独立审阅/验证分开，不自审自批 |

两人时A/B交叉评审，集成与测试轮值；第三人优先补集成/测试/运行能力，不只是再多做页面。具体姓名、GitHub账号和权限仍由Owner确认，不能把角色表当已授权名单。

QA/QC/IT和第三方投入不包含在“2–3名全职研发”的人数里。外部厂家可在我方代码基础承担有界工作包，通过相同PR/质量规则协作；只有明确人员、交付边界和依赖后才能重估其加速收益，不能线性相加人数承诺工期。

## 2. 每项任务必须按此流程

1. 先从[任务表](backlog.json)或Issue选择一个可验收结果，写明URS原编号、功能项、C控制、修改路径和明确不做事项。
2. QC给确认样例，研发共同确认接口/字段/状态/错误；质量规则不明时登记决策，按批准条件参数化，不在代码里擅自作决定。
3. 更新FS/DS增量和OpenAPI；前端Mock使用同一合同，后端实现真实PG命令。不要分别手写两套永远不同的模型。
4. 从最新已批准main建立短分支，一人/Agent一个worktree；在Draft PR尽早公开变更，不等待“全部写完”。
5. 交付同时包含UI、API、权限/资质、业务状态、版本/审计、正向/拒绝/并发测试、RTM和恢复影响。一个页面不等于一个可交付功能。
6. 在最新main合成组合上运行测试；非作者评审，质量关键变化由QC/QA确认；失败先修复，不删测、不降门槛。
7. 受控合并后自动部署合成测试环境并核对同一制品。生产部署仍需独立批准，禁止合并即生产上线。
8. 保留失败和纠正证据，更新任务/RTM，向下一人交付可复现入口、未决问题和版本。

PR #1专门收口规范。后续实现不继续堆在PR #1：待其获批合并后从合并后的main开发；现在可进行不接生产的资料/样例和环境准备。

## 3. 节奏、在制品与评审

建议两周一个迭代：周一确定一个主要业务结果和一个公共能力任务，周中合同/代码评审，周五QC演示及回归。每天短同步阻塞，禁止把开发时间消耗在长会。

团队同时最多两个主要工程任务；每人默认一个写任务。签名/权限/数据库迁移/合同等高冲突文件指定当轮唯一写者，其他人通过接口或评审参与。PR围绕一个结果，小到另一人能完整看懂；拆分不能割裂必要测试和安全控制。

每个达到试用门槛的模块安排约四周使用反馈窗口：准备与培训→受控任务→异常/边界→问题收口。窗口可以与后续模块开发并行，但必须有明确主本和准入，不能把“试用满一个月”当PQ通过，也不能用演示环境替代正式质量记录。

## 4. Definition of Ready：什么任务可以开工

必须有：业务场景/范围；URS和控制ID；确认或明确待决的规则；接口/数据变化；合成样例；正向与拒绝接受标准；负责人、评审人和依赖。

没有真实仪器或企业接口资料时，允许做明确标识的模拟器和适配合同，不允许将其标为真实联调完成。高风险规则未批准时，限制相关正式功能，不把整个工程全部停住。

## 5. Definition of Done：工程完成不等于正式可用

工程完成必须满足：代码与必要文档已审查；实际测试及失败处置记录；真实PG迁移/事务验证；权限范围覆盖列表/详情/导出/附件；前端与V3.1对照；必要性能和恢复影响说明；RTM引用实现/测试；锁文件及许可证/漏洞检查；可复现交接。

验证通过另需批准协议、适用环境、版本冻结、完整证据、偏差和独立复核；生产使用另需QA放行、SOP/培训、主本切换和运维准备。不得在任务标题写“完成”而正文仍大量NOT_RUN。

## 6. 小团队和AI开发技巧

先做一个有真实拒绝路径的样品动作，作为样板后复制架构；不要先把几十个菜单都做成空壳。每个领域复用同一身份、签名、审计和版本服务，复用的首先是规则不是页面代码。

Agent适合生成CRUD骨架、类型、测试、文档差异和重复性重构；人负责业务规则、风险与最终评审。任务提示词必须带固定base、允许路径、URS/C编号、禁改范围、验收命令、数据授权和停止条件。Agent不能自己编法规、自己Approve自己的PR、读取生产数据或以截图代替执行。

实现者与复核者分开上下文；独立复核从远端diff和实际测试证据开始，不只阅读实现者总结。避免多Agent同时写同一分支；禁止reset/clean/stash他人工作。每次结束写[交接记录](../templates/HANDOFF.md)。

用一套合成金数据覆盖正常、超限、资质失效、过期、双人确认、退回、版本冲突和恢复。固定时钟用于测试，生产使用可信时间；不得把测试日期/密码带入正式系统。

先探测最难Word模板、一个通讯源和一个CDS/文件来源，再扩展大量普通表单。每四周及首个闭环后复盘实际吞吐、返工和外部等待，更新[容量模型](capacity-model.json)，不凭AI工具或增加人数拍脑袋缩期。
