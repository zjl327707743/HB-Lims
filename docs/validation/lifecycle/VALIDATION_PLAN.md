# VP-HB-LIMS-001 项目验证计划草案

版本：0.1；日期：2026-11-20；状态：**PLANNING_DRAFT_NOT_APPROVED**。依据原 URS-2107–2109、[SIA](SYSTEM_IMPACT_ASSESSMENT.md)、[LC 规则](../../standards/sdlc-validation/LIFECYCLE_STANDARD.md)。企业级 VMP、适用范围、人员及质量批准尚待实际确定。

## 1. 目标与方式

以 GAMP 5 第二版的风险与生命周期方法组织自研：需求/风险/设计与测试同步迭代；每个候选版本固定范围、制品、配置和环境；按批准策略利用可信研发/供应商证据；正式使用前完成适用确认、偏差/总结与企业批准。设计满足预期用途和数据完整性，不能承诺监管必定接受。

保留 Next/React/AntD/FastAPI/PostgreSQL 等当前技术方向。前期工程先形成带权限、原始记录、审计、版本、失败路径的最小纵向结果，逐步扩展；不得把全部功能做完后再集中补验证资料。

## 2. 职责与独立性

| 角色 | 负责内容 | 不能替代的职责 |
| --- | --- | --- |
| 流程 Owner / QC | 用途、需求、方法/标准、代表场景、业务验收和日常程序 | 不能用开发者猜测代替质量业务规则 |
| 系统 Owner | 系统清单、生命周期计划、运行/变更/接口协调 | 不能因外包验证转移企业责任 |
| 研发 A / B / 可选 C | FS/DS/CS、代码/迁移、工程测试、证据及整改；互相审查 | 作者不得以另一个账号或 Agent 假充独立人审 |
| IT / 安全 | 基础设施、网络/身份、支持、备份恢复、环境和访问 | 不能只提供服务器而遗漏安装配置/恢复证据 |
| QA | 按质量体系批准适用性、风险、策略/协议、偏差和质量使用 | Owner 接受开发规划不自动等于 QA 批准 |
| 第三方验证人员 | 提前评审设计/协议、执行/见证、独立核验证据、偏差与总结 | 其开发成果仍需非作者复核；报告不能替企业放行 |

QC/QA/IT/服务商投入不包含在“2–3 名开发者”人数中。实际兼岗须记录冲突与补偿控制；本表不给未知人员虚构任命。

## 4. 原 URS 资料包逐项保留

## 5. 风险和测试安排

采用初始定性优先级安排工作；概率信息不足明确未知，不编造 RPN。关键控制以失败/拒绝/边界/并发/恢复测试为重点；正向业务贯穿首条闭环。每项测试关联 URS/风险/设计与目标基线，工具/环境适用性按影响评估。采用 [TEST_STRATEGY](../../standards/sdlc-validation/TEST_STRATEGY.md)；可复用已审阅工程/供应商证据，不机械重跑，也不自动采纳。

任何正式验证活动（包括 G1/DQ）的协议、接受条件和对应授权都应在该活动执行前具备；不得先执行后倒填批准。G3 前确认后续候选验证协议的批准角色、证据接收标准、目标环境、数据、接受阈值与阶段划分。任何变更导致版本/环境/配置差异时重评可复用范围。法规或指南的示例频率、风险分数不成为本项目默认参数。

## 6. 资料与证据控制

工程规格、模板、合成测试和脱敏摘要由 Git/PR 受控；企业质量签名、原始验证结果和真实数据进入企业批准的受控库。每项资料至少有 ID、版本/日期、范围、职责/审批、关联、存储/保留和变更历史。GitHub Actions 临时 artifact 不是唯一长期验证档案。

研发、工程测试、验证执行、独立复核和质量放行保持不同状态。机器检查只验证脚本能检查的结构/引用/版本，不能认证人员资格、签名真实性或现场事实。

## 7. 偏差、变更与使用决定

保存原失败和后续整改/复测；重要偏差评估数据和业务影响，关键未解问题阻断其用途。规格/代码/配置/接口/补丁变化按 LC-009 处理。VSR 根据实际执行与残余风险形成范围明确的结论；最后由授权角色批准特定版本、配置、环境、用途、限制和主本切换。

## 8. 运行与再评估

运行前具备操作/维护、权限/审计复核、事件/变更、备份恢复、连续性、培训与归档程序。周期评价间隔由风险/实际运行/企业决定；接口、法规、重大故障、支持结束、用途变化、迁移或退役触发专项评估。

**当前批准状态：未批准。** 计划中职责和资料框架可用于开发准备；正式质量使用仍需实际协议、执行、偏差处置、审阅和批准。
