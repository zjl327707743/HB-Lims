# 2–3 人团队每次迭代怎么做

本页补充现有 [开发手册](../../delivery/TEAM_PLAYBOOK.md) 和 [路线/周期](../../delivery/ROADMAP.md)，不重新承诺上线日期。新增规范不改变开发顺序；减少后期返工的方法是让设计、测试和证据跟着每个纵向结果一起完成。

## 第一次工程开工

1. Owner 安排真正的非作者审查 PR #1，落实仓库保护/权限；按项目批准流程形成工程基线。不要把规范 PR 混成业务实现 PR。
2. QC/QA/IT 用 SIA/VP 草案确认第一阶段用途、记录主本、关键角色与签名、数据/方法规则、环境和证据保管。只阻断受未决值影响的质量规则；布局、合成接口、安全基础可以同时准备。
3. 团队选择第一条很小但完整的业务切片，例如“授权人员接收已请验样品，保留原记录、审计和并发冲突”。原闭环中的取样/分配/结果/复核/异常/报告按依赖递进。
4. 第三方尽早审查本次规格、风险和测试接受方式，确认以后哪些开发证据可直接利用；不要等完整系统做完才第一次联系验证人员。

## 一个工作项的完整做法

| 顺序 | 开发者实际动作 | 同步更新 | 完成判断 |
| --- | --- | --- | --- |
| 1 领任务 | 固定 base/head、范围、URS、风险、允许路径 | TASK_BRIEF / DEVELOPMENT_CHANGE | 接受条件与未决事项明确 |
| 2 说明行为 | 写正常及拒绝/失败条件；关键值向 QC/QA 求证 | 领域 FS/DS/CS | API、数据/状态和控制边界可审阅 |
| 3 并行实现 | A 数据/API/迁移；B 页面/契约集成；可选 C 集成/故障测试 | 代码、配置、测试 | 首版即包含权限/审计/版本/更正等适用控制 |
| 4 验证结果 | 执行合成环境测试，保留失败和重测 | 运行证据、偏差、RTM 引用 | 真实版本对应真实结果；未测明确 |
| 5 独立审查 | 另一名合格工程人员审代码/风险/证据，QC 看业务 | PR 和设计/缺陷记录 | 检查通过且发现已处理；不假充 QA |
| 6 交付候选 | 更新版本/配置、部署说明与回退影响 | 发布清单、交接 | 能重现和演示；正式用途仍按 G3/G4 |

不必每个 PR 再抄一整本 SIA/VP。若用途/风险/规格/验证/运行没有变化，在任务中引用已有版本并说明不影响的理由；有变化就更新受影响部分。

## 如何切分首批工程 PR

- **工程骨架和控制基础：** 精确依赖/镜像、开发环境、主题映射 V3.1、OpenAPI、真实 PG/Alembic；账号/对象授权、版本、审计事务等公共能力先有可测骨架。
- **样品接收纵向链：** 合成请验/取样前提，接收、查找、权限拒绝、重复/并发及审计失败；网页和 API 一起验收。
- **检验记录与计算：** 受控方法/模板、单位与修约、首次原值、更正/版本、边界金标准；不先做任意脚本编辑器。
- **复核、异常、签署和报告：** 明确 OOS/复测采用、独立复核、签名绑定、报告原始版本、导出/打印轨迹；不能用合格复测覆盖首次失败。
- **候选恢复与接口：** 真正恢复演练、文件/对象/任务一致性、外部真实协议和失败回执，再扩稳定性/留样/EM/复杂设备。

这些是可拆分主题，并非每项只能一个 PR，也不是先完成全站页面后再补后端。每个 PR 保持可审查范围，以实际完成的纵向结果推进。

## 节奏与周期怎么估

可以用 1–2 周迭代安排和周度业务演示，这是团队节奏建议，不是法规周期。前 2 个迭代用于确认设计/接口与第一条真实纵向切片；其后按实际完成量重估首个试点。复杂 LES 模板、仪器、方法/公式、迁移和 QA 决策通常不能用页面数估工时，按风险与外部依赖单独排。

沿用仓库既有 capacity-model 和 ROADMAP，不把“规范补齐”折算成开发完成。计划中显式留出业务评审、独立代码审查、失败修复、资料整理、第三方执行与再测。每个里程碑用可演示结果和证据判断，不用模板数量判断。

## 交给 Agent 的任务正文

> 阅读 AGENTS.md、TECH-V1、相关 DEV/LC、SIA/VP 和当前任务。实现指定范围的一个纵向结果，保持 V3.1 风格。先给 URS/子需求、风险、FS/DS/CS 与正常/拒绝接受条件；未决质量参数单列并继续无关工程。代码、迁移、配置、测试与文档同批提交；使用合成数据，保留真实命令/结果/失败与复测、源码/制品/配置引用。不要代填 QA 批准、接受残余风险、改原 URS 或降低门禁。回传变更、证据、未测/受阻、运行恢复影响和非作者需审查的问题。

## 每周十分钟核对的问题

本周完成了哪项可用业务行为？拒绝/故障是否实际测过？新需求或关键值谁决定？已失败的测试怎样处理？证据是否对应当前版本？第三方将来能否读懂？谁负责下个阻塞？这些答案应来自真实记录，而不是在周报里重新创造一次。
