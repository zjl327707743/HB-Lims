# 自研系统测试与验证证据策略

状态：候选策略，正式采用须纳入批准的 VP/协议。来源：S01 §4.7、S02 §3/8–12（官方全文补缺）、S05 D5/D8/D9、原 URS-2108/2109；适用边界见 [来源评估](SOURCE_ASSESSMENT.md)。

## 先确定“要证明什么”

测试从真实业务风险出发。先给需求定义客观接受条件，再选择最低但充分的验证办法。代码覆盖率、用例总数、截图数量和“全流程点击一遍”都不能单独证明质量风险已受控。

| 需要证明的事实 | 推荐证据 | 重要限制 |
| --- | --- | --- |
| 规格能够满足预期用途 | 需求/设计审查，风险与数据流分析，DQ 或批准的等效审查 | 模板存在不能证明设计正确 |
| 自研规则与算法正确 | 独立代码审查、单元/属性/金标准测试 | 不能用同一算法生成期望值再验证自己 |
| 持久化和跨组件行为正确 | 真实 PostgreSQL 的约束、事务、并发、迁移；对象/队列契约和故障测试 | Mock 无法证明真实数据库锁、事务、S3 权限或设备行为 |
| 角色、顺序、记录、签名受控 | API 拒绝、端到端、审计/签名/原始数据关联检查 | UI 隐藏按钮不等于后端授权 |
| 指定制品正确安装配置 | 受控清单、实际版本/配置核对，适用 IQ | Docker 镜像构建成功不是现场安装确认 |
| 业务在批准范围内可用 | 受训用户操作真实业务代表性场景，适用 PQ/UAT | UAT 不能代替安全/恢复/计算等技术测试 |
| 持续运行和故障可恢复 | 负载、容量、掉电/进程/依赖失败、备份恢复、业务连续性演练 | 备份文件存在不能替代恢复核对 |

## 测试层级不与 IQ/OQ/PQ 一一等同

单元、集成、系统、端到端说明测试对象；DQ、IQ、OQ、PQ/FAT 说明批准验证策略中的用途。一个适当的工程测试可以支持某个验证活动，但须审查目标版本、预期、工具/环境、原始输出、执行和复核是否满足要求。

原 URS-2109 列明的每项交付应在 [验证计划](../../validation/lifecycle/VALIDATION_PLAN.md) 中保持映射。允许合并文件或按批准策略利用已有证据，不允许在任务执行时自行宣告 FAT/PQ 不适用。

## 三种测试形式

1. **预定义自动化测试：** 用例和断言受版本控制；记录实际运行命令、目标、数据、环境、工具、结果及原始输出。按工具用途、配置和高风险断言模式选择代表性失败挑战，确认失败可被检出，避免“脚本退出 0”但断言从未执行；不要求每条测试再配一套独立变异测试。
2. **脚本化人工测试：** 规定前提、输入、步骤、期望和记录方式；执行当时填写实际观察，保留异常与证据。截图应证明必要事实，不为每次点击机械截屏。
3. **有记录的探索测试：** 先定义任务章程、风险/覆盖目标、范围/时间、数据和记录方式；记录实际路径、观察、问题与结论，必要时形成可回归用例。涉及关键预定接受标准的证据不能用事后改写章程替代。

## 首条闭环优先验证的反例

| 场景 | 必须观察的结果 |
| --- | --- |
| 未经授权的跨实验室查询、详情、附件、导出或已撤权资源请求 | API 统一拒绝，不能依靠前端缓存继续泄露；获授权的跨实验室角色仍按其实际范围工作 |
| 同一样品接收重复提交、同键不同内容、并发更正 | 结果可查询且不重复；冲突明确；不会静默丢失更新 |
| 业务提交时审计写入失败 | 关键写入回滚或按已批准一致性策略阻断；不得成功但缺审计 |
| 用旧版本签名、签名超时重试、本人违规复核 | 签名绑定准确版本和意义；拒绝不合法签署，不重复批准 |
| 原始 OOS 后复测合格、更正、方法换版 | 原始结果和调查链仍在；采用和批准有依据；历史不被新规则重算覆盖 |
| 附件半上传、错哈希、报告模板变化、任务重投递 | 未完整文件不得成为可信原始数据；报告版本一致；不重复业务效果 |
| 真正恢复数据库及对象、审计、签名和待处理任务 | 代表性记录可读、关联完整；恢复后不再次执行已完成审批 |

本表是接受方向；具体数据、数值和适用规则在领域规格/协议中批准。受限条件缺失时写 BLOCKED 或 NOT_RUN，不编造默认值。

## 性能场景

保留原 URS-103“不低于 20 并发”、URS-104“页面不超过 3 秒、报表不超过 20 秒”的原要求；数百注册人员与实际并发分开建模。明确代表性样品/结果/附件数据量、操作组合、报告复杂度、浏览器/网络、计时起止、持续时间和错误率。可以增加 p95/p99 等分析指标，不能用其替换原接受口径；异步入队时间不能冒充报告生成时间。

## 环境与工具适用性

在正式采用测试前记录与生产的差异：镜像、DB/存储/队列版本、权限、网络/认证、时钟、配置、数据规模、浏览器/字体/打印和仪器。逐项决定影响、可复用部分与需要现场补测的部分。功能等效环境可按批准策略用于相关测试；最后仍要证明目标环境的安装、配置和必要接口行为。

工具评估的实际检查可包括：能否发现已知失败、漏跑如何暴露、断言来源是否独立、日志/时间/版本是否完整、原始证据能否保存、更新如何控制。通用 Git、编辑器不自动需要整套应用 CSV；直接迁移或更改质量记录的脚本则必须按其质量影响验证。参考 [工具与供应商模板](../../templates/validation/TOOL_SUPPLIER_ASSESSMENT.md)。

## 复用证据的决定

逐项记录：原用例/报告及受控版本、目标需求/风险、供应商或研发质量过程、实际制品/配置/环境、测试方法/数据/接受标准、失败和已知限制、真实性/完整性可审阅程度、本项目差异、补测、审阅与决定。证据只覆盖自己实际证明的事实；通用数据库测试不能证明本项目事务逻辑。

## 执行与归档

正式执行前确认协议和前提；执行后保留原结果、版本与所有偏差；修复影响触发回归范围重评；VSR 与 RTM 引用实际证据。公开仓库仅放合成用例、定义和不泄密引用，正式原始证据按企业受控存储策略保存。现有 [工程证据校验](../../validation/ENGINEERING_EVIDENCE.md) 只校验已实现的结构/引用/版本规则；不能认证人的资格、签名或日志真实性。
