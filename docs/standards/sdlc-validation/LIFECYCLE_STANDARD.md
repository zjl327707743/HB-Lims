# LC-V1 自研系统开发、测试、变更与代码管理

版本：1.0；编制日期：2026-11-20；状态：PR_PROPOSED，QA_APPROVAL_NOT_GRANTED。以下“必须 / 不得”是 HB-Lims 选定的工程规则；来源条款的法律性质和适用条件见 [来源评估](SOURCE_ASSESSMENT.md)，不得把具体实施选择反称为法规原句。

## LC-001 用途、系统边界与影响评估

**关联：DEV-001/005/027；G0/G1/G3。依据：S04 第 1、3、6、7、11 条；S01 原则、§4.3；S02 §1、5–6；S05 主文 §2–4、M1/M3。**

- 在承接质量用途前建立系统清单和 SIA，说明业务过程、适用厂区/产品/市场、记录类型及主本、功能和接口、基础设施、运行与管理人员、系统 Owner、外部服务及失效影响。以实际用途判定 GxP 影响；软件名称、部署位置和使用人数不是结论。
- LIMS 自主数据库、应用和发布仍须覆盖身份、时间、文件、备份、仪器等依赖。HBOS 仅链接时记录链接边界；承担 SSO 时纳入身份接口、停用/撤权、认证故障和上游变更影响。不能把 HBOS 整体无条件拉入，也不能忽略真实依赖。
- 按记录类型区分电子原始数据、必要元数据、纸质原件、真实副本和报告。明确报告审核与产品批放行的边界，不把“报告批准”自动扩展为法规意义的产品放行。
- 用途、接口、产品市场、部署、记录主本或法规变化时重新评估；待决事项仅阻断受影响设计/质量动作，合成数据工程准备可以继续。

**接受证据：** 可审阅的 SIA、数据流/边界图、系统与服务清单、适用性矩阵、待决清单。风险范围的接受由相应 QC/QA/Owner 决定。

## LC-002 生命周期计划、职责与风险方法

**关联：DEV-001/003/015/027/028；G0–G5。依据：S04 第 3–6、8、12 条；S01 §1–4；S05 主文 §2–8、M1/M3/M4/M7。**

- VP 应预先说明生命周期方式、阶段产物、质量评审点、风险方法、测试策略、供应商证据复用、环境和偏差处理、放行、维护及退役责任。URS 所称 VMP/VP 与企业级 VMP 的关系必须明确；项目 VP 不冒充整个工厂的验证总计划。
- 可按短迭代开发；每个候选版本有可识别需求与配置基线，G1/G3/G4 的评审不因敏捷取消。原型和工程试验标明用途；未批准的试验数据不进入正式质量记录。
- 自研业务模块按定制软件的控制深度管理；基础设施、现成产品、受控配置、自研代码分别评估。GAMP 软件类别与风险等级不是同一件事；类别不会自动决定是否需要某一测试阶段。
- 风险记录至少包含功能/数据、失效模式、质量后果、初始风险及理由、控制、验证办法、实施证据、残余风险、接受人/依据及复核触发。不要求为了填表编造软件失效概率或统一 RPN；严重质量后果不能靠低概率评分被自动接受。
- 2–3 名开发者可分担多项工程职责；关键代码由非作者审查。QC 定义业务，系统 Owner 管用途与运行，IT 管基础设施，QA 按企业质量体系批准，第三方按合同执行。兼岗冲突和补偿措施需明确，不以供应商名称代替独立性。

**接受证据：** VP、职责矩阵、组件分类理由、风险台账；残余风险必须在控制实现/验证后重新评估，初始规划不能写“已降低/已接受”。

## LC-003 需求、FS/DS/CS 与双向追溯

**关联：DEV-001/002/012/026；G1–G4。依据：S01 §4.4–4.8；S02 §5–7；S05 M5、D1/D3/D8。**

- 保留原 185 条 URS 的编号、正文、来源。分解后的子需求、业务规则和接受条件应指回原编号；保留原型风格约束。原文歧义通过受控差异/决定解决，不能修改源文使结果“符合”。
- FS 描述可观察业务行为：角色/资格、正常及禁止顺序、输入/输出、关键字段、异常、审批、更正、复测与接口；DS 描述实现：领域状态、数据关系、事务/审计/签名边界、API、故障、并发、安全和恢复；CS 描述实际版本与关键参数、环境差异、访问、时间、保留、任务、报告和方法配置。
- 同领域可以采用 FS/DS/CS 合并文件，但上述内容、版本、责任人和相应审核范围须清晰。通用技术架构文档不能代替具体业务规格。
- 每条范围内需求可追到风险/控制、规格或程序、实现/配置、验证办法、执行/偏差和结论；反向能从测试、变更和发布定位受影响需求。允许多对多和经批准的程序性控制，不强迫每条 URS 对应一个代码测试。
- 在正式执行前确定客观接受条件；对公式、单位、修约、权限、签名、OOS、主本等关键规则先取得业务依据。探索可以发现新需求，但不能测试后倒填“预先批准”的标准。

**接受证据：** 可测试的规格、URS 差异、RTM、版本和审核记录；裁剪的需求保留理由/决定，不用删除行表示不适用。

## LC-004 编程规范、代码审查与 Agent 使用

**关联：DEV-004/005/011/025/026/028；G1/G2/G3。依据：S02 §8.1–8.4；S05 D4/D8/D9/D11；S04 第 8、12、13 条。**

- 业务代码、数据库迁移、API/事件契约、权限策略、报告/方法配置、测试和运维脚本受版本控制。采用当前 TECH-V1；由后端统一执行业务权威，Web、worker、导入和管理员入口不得绕过。
- 一个工作项交付一个可验证的纵向结果；提交能定位需求、风险和设计。工作分支可以迭代；进入共享受控分支前通过约定检查和非作者代码审查。不允许通过重写历史、删测试、禁用检查或改接受标准掩盖缺陷。
- 审查内容依风险覆盖：授权与角色分离、状态/签名版本、原始数据和更正、事务及审计失败、幂等/并发、计算精度、迁移、外部输入、依赖、错误处理和可测试性。关键算法的期望结果由独立方法或经批准参考数据产生。
- Agent 可以起草设计/代码/用例、运行授权的工程测试；提交中说明其改动范围、所用工具/版本（可取得时）、采用内容和人审结果。无需为每次普通补全归档全部聊天；影响质量规则或重要设计的决策依据应保留可审阅摘要。
- Agent 不得代签、接受残余质量风险、伪造测试输出或批准，不得擅自接入生产数据。产品内引入 AI/ML 质量决策属于新的用途/风险/验证范围，不能沿用“开发辅助工具”结论。

**接受证据：** Issue/任务书、代码及设计差异、非作者审查、实际检查输出、未测/已知缺陷。代码作者的另一个 Agent 可以技术复核，不能伪装成人的审批。

## LC-005 配置、构建与可识别发布基线

**关联：DEV-012/021/025/027；G2–G5。依据：S01 §4.3、10；S02 §6、8.5–8.7（官方补全）；S05 M8、D5/D8、O6。**

- 每份候选基线包括源码 SHA、依赖锁与 SBOM、基础镜像/应用制品 digest、构建工具、数据库迁移、配置摘要、方法/规格/模板版本、时区/字体/浏览器/转换器、接口版本和环境差异。密钥只记录安全引用和轮换影响，不写入公共清单。
- 使用受控构建产物推广；验过的制品、环境和配置均可识别。不能重建不同产物后仅凭源码相同继承结论。Next 构建期变量或报表字体变化亦须识别其影响。
- DEV/TEST/验证/PROD 的用途、数据、权限和密钥应分离；测试环境是否等效逐项论证。正式执行时登记实际安装/配置，并与批准基线核对。
- 生产禁止自行拉取 latest、未审自动升级、启动时各实例竞争执行迁移、在线随意改代码。受控配置更改进入变更流程；经授权日常业务配置按既定 SOP 和审计路径执行。
- 保持已发布版本可重建、可追踪、可恢复的必要材料；不能把“可重建”当作必须逐字节重现所有外部供应商环境的绝对保证。无法重建的外部组件须有取得/保存/替代方案。

**接受证据：** 发布清单、实际安装/config 对账、环境差异评估、受控构建和迁移/恢复记录。

## LC-006 风险驱动测试与证据利用

**关联：DEV-003/013/023/027；G1–G4。依据：S01 §4.7；S02 §3、8–12（含官方补全）；S05 D5/D8/D9。**

- 采用 [测试策略](TEST_STRATEGY.md) 选择代码审查、单元/集成、接口、端到端、安装配置、业务适用、负载、故障恢复等验证活动。高风险质量控制重点检验拒绝、边界、错误、并发、重试和恢复，不用覆盖率百分比代替风险覆盖。
- 正式协议预先界定版本、前提、数据、步骤或探索任务章程、接受条件、证据方式、执行/复核角色。允许有记录的探索测试，但正式采用所需上下文、实际观察和结论必须可审阅；“无脚本”不等于无记录。
- 自动化测试的断言、失败检出、证据输出和目标环境需证明适合用途。工具评估的范围取决于其影响，不把所有开发工具再次当成完整 LIMS 验证。
- 研发或供应商证据复用逐项记录对应需求、原版本/环境/方法、执行可追溯性、差异、缺陷状态、补测与接受人。既不机械重测全部，也不能只凭供应商合格证/CI 绿灯跳过适用性判断。
- 测试使用合成/经授权数据；生产环境中不得为“验证”制造无标识真实质量记录。环境等效和安装差异按批准策略处理。

**接受证据：** 风险到测试的映射、协议/任务章程、工具/环境评估、原始输出、复用决定及缺口补测。阶段名字由批准策略和 URS 决定，不把 unit test 自动改名 OQ。

## LC-007 缺陷、偏差、复测与结论

**关联：DEV-003/009/014/027；G2–G5。依据：S01 §4.2、13；S02 §3、8.7；S05 D5、M7、O3。**

- 区分工程缺陷、协议执行偏差、业务质量事件和风险接受。相同问题可互相引用，不能因名称不同失去质量影响评估。
- 每次执行保留目标版本、实际结果、原始证据、执行人/时间；失败、受阻、重跑和通过分别保存。不删失败截图，不用最后一次成功覆盖历史结果。
- 偏差记录事实、影响范围、初步控制、根因（确认前明确待调查）、整改、回归范围、复测、残余风险及处置人。结果异常不先改预期来变为通过。
- 修复后的证据必须属于被放行候选；较晚失败不能由旧通过覆盖。重大/关键未解决问题阻断其影响用途；非阻断偏差也须有客观理由、限制、责任人、到期措施和授权接受，不能自动到期放行。

**接受证据：** 缺陷/偏差台账、原执行与复测关联、版本对应、审阅结论；机器引用校验不能证明记录真实或批准者合格。

## LC-008 供应商、服务与生命周期工具

**关联：DEV-015/017/019/025/028；G0/G1/G3/G5。依据：S04 第 4、8、12 条；S01 §3；S02 §4；S05 主文 §7–8、M2、D9/D11、S1。**

- 依使用风险评估开源依赖、数据库/对象存储、云/IT、仪器接口、身份服务、验证服务商及内部开发服务。记录能力、维护支持、漏洞/许可证、数据所有权、备份/退出、变更通知和责任接口；开源软件无商业审计报告并不自动禁止使用。
- 质量协议或等效内部职责协议明确谁编写、测试、评审、保留证据、处理偏差和批准使用。验证服务商可执行/见证，企业责任不转移；若第三方同时开发，独立审查安排必须显式。
- 工具清单按实际用途分类：仅辅助开发；生成/评价验证证据；直接写入/迁移质量记录。依风险采用配置核查、挑战测试、输出复核、人员培训和访问控制；最后一类须按其 GxP 功能处理。
- Agent/模型版本可能变化，依赖人的审查、可重复工程验证和受控输出建立信任。不能宣称模型供应商替项目承担验证，也不能把提示词或工具品牌当正确性证据。

**接受证据：** 供应商/工具评估、责任协议、准入与复用决定、持续监控触发。生产存储产品等未决项继续保留，不以本规范暗自选定。

## LC-009 变更、补丁与紧急处理

**关联：DEV-004/012/024/025/027；G1–G5。依据：S04 第 17 条；S01 §10–11；S05 M8、O6、S4。**

- 开发中未批准草稿按版本控制和工程审查推进；已批准需求/设计、验证候选及在用系统的变更需受控影响评估。普通草稿探索不必每次请求 QA 批准，但影响关键质量规则时须取得对应决定。
- 变更单记录原因、前后基线、URS/设计/风险、代码与配置、历史数据/签名/接口、SOP/培训、测试/再验证、回退或 forward-fix、批准和关闭。规格变更必须同步验证影响，不能只记录代码差异。
- 标准变更预先批准类别与条件；紧急变更按应急程序取得授权、保存最小必要评估/证据、限定用途并及时补完评审；临时变更有期限、恢复或转正式安排。禁止事后伪造事前批准。
- 漏洞补丁评估“实施风险”和“延迟风险”，据影响选回归，不默认全套 IQ/OQ/PQ，不无限冻结有风险版本。供应商自动更新需进入可审查/可控制的机制。
- 影响验证状态或关键质量功能时，在完成必要评估和接受前禁止用于该质量用途。例外不能由开发者/Agent 自动关闭。

**接受证据：** 有范围的变更记录、评估/批准、实际部署、测试和版本对账、关闭或受控限制。

## LC-010 验证资料包与质量使用批准

**关联：DEV-001/003/027；G3/G4。依据：S04 第 6、8、13 条；S02 §3、9–12；S05 M1/M7；原 URS-2107–2109。**

- 资料包至少逐项交代 URS 约定的 VMP/VP、深化 URS、FS、DS、DQ、RA、FAT、IQ/OQ、PQ、RTM、VSR、随机资料、OM/MM；配置规格、源代码管理、数据迁移、恢复、安全/性能、SOP/培训作为相关资料并入索引。
- 文件可组合或用等效证据支持，但须记录具体映射、适用理由、缺口与批准。尤其 URS-2109 已列 FAT/PQ 等时，不可仅依据通用指南擅自删除。
- 协议、执行原始资料、偏差、总结与批准分别有受控身份和版本。VSR 汇总实际范围、通过/失败/未执行、需求风险覆盖、未关闭问题、环境/版本、限制、培训/运行准备及建议，不写笼统“全部合规”。
- 最终使用决定明确产品版本、配置、环境、厂区/业务用途、记录主本、限制和批准者。源码合并、部署完成、用户试用、质量试点各自有边界，不能互相替代。
- GitHub 可作为工程记录来源；只有企业经过适用性评估并批准其满足对应文控/签名/归档要求时，相关记录才能按指定用途被正式利用。普通 PR approve 不是自动满足所有法域的电子签名。

**接受证据：** 完整资料索引、已执行 RTM、偏差处置、VSR、培训/运行/切换准备、真实的企业质量批准。

## LC-011 运行、周期评价与受控复核

**关联：DEV-006/010/014/015/021/022/023/027；G4/G5。依据：S01 §7、9、11–16；S04 第 14–21 条；S02 §11、13；S05 O1–O13、S2/S4。**

- 运行前确定账号/权限、数据与审计复核、备份恢复、监控/事件、变更、业务连续性、服务支持及周期评价的程序、责任和培训。频率按风险、记录用途及企业决定，不从指南示例直接复制固定周期。
- 周期评价综合功能/配置变化、事件与偏差、用户权限、审计复核、容量、恢复、供应商与漏洞支持、培训及验证状态；结果驱动必要整改/再验证。
- 周期评价核销上次行动；未完成事项明确责任人、期限、继续使用限制和逾期复评，不只重复列问题。运行交接包括企业可访问的自研源码、合法依赖、受控制品、构建/安装/配置与恢复说明、历史证据位置，并由另一授权人员确认能够识别和恢复目标版本、检索代表性记录。
- 备份成功不等于恢复成功；数据库、对象、元数据、审计、签名、模板和待处理任务需验证一致恢复及后续安全运行。恢复后不得重放出第二次业务批准。
- 未来若引入“按异常复核”，先定义完整主记录、异常规则/版本、缺报侦测、筛选准确性、人工责任和比较验证；即使没有异常也须有完成记录。当前 MVP 不得凭“无异常”自动省略既定复核或质量批准。

**接受证据：** SOP、培训有效性、权限/审计复核、监控事件、恢复演练、周期评价和后续措施。

## LC-012 迁移、归档与退役

**关联：DEV-017/022/023/024；G1/G3/G5。依据：S04 第 9、18–21 条；S01 §4.8、17；S02 §13.13–14；S05 D7、O13；S09 官方补全 §7。**

- 设计阶段就识别记录保留和退出需求：原数据、必要元数据、单位/精度/时间、关系、审计、签名和版本、可解释方法/配置，按记录类别确定保留期限、起算点和 legal hold。
- 迁移计划预先定义范围、映射、转换规则、验证抽样或全量核对、差异处置、试迁移、回退/切换、权限和证据；验证数值与含义均保持，行数/哈希相同不能单独证明语义正确。
- 退役须评估受影响接口、活动任务/签名/数据，记录封存、检索工具、访问责任、周期可读性检查、保留/销毁批准。必须实际检索代表性记录及其审计/签名关联，不能只交出数据库备份文件。
- 归档、备份、灾备分别定义用途。生产历史记录、验证资料和系统文档的保存期按其适用义务确定；不以原 URS“至少五年”设定全库五年自动删除。

**接受证据：** 迁移/归档/退役方案及实际核对、可读性和关系完整性、受控移交及销毁授权。

## 执行优先级

首个工程 PR 前先明确相关用途、业务负责人、验收和风险；首条纵向链同时实现权限、原值、更正、审计、版本和失败处理；第三方在规格和测试策略阶段介入；候选冻结后完成批准协议下的执行、偏差、总结与使用批准。各阶段只扩展已经选定的用途，不能以缩小试点为理由裁掉该用途必需控制。
