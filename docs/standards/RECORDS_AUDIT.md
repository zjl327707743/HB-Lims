# REC-V1 原始记录、受控草稿与审计复核（C02/C03）

来源：URS-110/601/603/604/610/616/622/1901/2105，功能表5/7/25/26–28；法规定位见[REG-V1](REGULATORY_SCOPE.md)。以下为本项目工程要求，不是声称法规逐字规定某种数据表结构。业务测试当前NOT_RUN。

## REC-01 原始数据和保存边界

FS必须定义活动开始、采集/人工输入确认、受控保存、提交、签署、中断及更正的边界。URS-601要求每次保存保留历史版本并支持定时保存。质量原值在活动发生时进入受控记录；不能只留下最后一次提交，不能用可随意清空的localStorage作为正式原始记录。

原始值、仪器原始字节、方法/标准/公式/资源引用、实际操作者、设备身份和时间关联保存。初始超限值、未完成执行、失败采集、终止原因和后续复测保留关系。网络中断时界面明确未受控保存/待确认，不显示成功；离线采集仅由获准的持久缓冲代理承担，不能默认浏览器离线可完成正式签署。

受控草稿采用版本号、并发校验和自动保存回执。每次保存可追溯，但不机械地把每次按键都当一份正式记录。恢复时检查对象版本，禁止覆盖另一人的较新修订。记录号稳定、唯一；作废/终止保留理由，不物理删除。

## REC-02 受控更正

已保存值的修改建立新修订，保留前后值、原因、人员、时间及关联；已签署内容更正需要重新走适用复核，原签名仍绑定旧版。普通字段默认值不能替代实际观察；默认值来源和人为确认按方法规则记录。

业务写入、签名（适用时）、质量审计、Outbox同一PG事务。鉴权失败、数据库失败和安全事件使用独立日志渠道；不把失败命令的临时状态误写成业务成功。哈希是完整性辅助，不替代权限、保留、可读性和独立审阅。

## REC-03 审计复核工作台

复核人员在检验记录上下文查看：首次结果、全部更正、重测/重采样、结果采用或失效理由、手工导入、标准/模板/公式版本、签名和打印历史。列表、统计和导出遵守相同权限范围。

记录复核的范围/截止点、规则版本、审阅人、发现项、结论及处置；复核后新增质量变化使受影响的复核失效或重新待审。关键未决项按批准规则阻断后续批准，不能依靠人记住某条日志。

若用异常规则减轻人工阅读，规则必须版本化、覆盖性可证、可回看完整底层记录；不得通过过滤隐藏首次OOS或“已恢复正常”的异常。日志数量不能作为审计有效性的替代指标。

## REC-04 必须保留的拒绝与恢复测试

| 用例族 | 最小场景 | 所需证据 |
| --- | --- | --- |
| REC-RAW | 超限值保存后关闭、刷新、断线、再次采集 | 首次值及修订仍可追踪，未保存状态不误报 |
| REC-CONFLICT | 两终端同改草稿、重复提交、超时查单 | 版本冲突、幂等结果和数据库事实一致 |
| REC-CORRECT | 无原因更正、修改已签署版本、越权查看历史 | 拒绝证据；获准更正有完整旧版和签名关系 |
| REC-REVIEW | 已复核后新增修订、规则漏报、复核人越权 | 重新待审、异常定位、完整审阅记录 |
| REC-ADMIN | 应用账户删审计、管理账户紧急修复 | 权限阻断或独立受控运维记录，不声称超级用户绝不能改数据 |

证据格式使用[验证证据模板](../templates/VALIDATION_EVIDENCE.json)。业务正向、拒绝和恢复都实际执行后，才可更新对应RTM；当前仅定义用例，不填写PASS。
