# SEC-V1 身份、授权、电子签名与审计

本文件为工程控制要求，法规适用和签署方式由QA依据预期用途确认。采用JWT并不自动产生电子签名或数据权限。依据见 [SOURCES](SOURCES.md)。

## SEC-01 登录与SSO

LIMS独立域名和浏览器会话。默认采用Next薄BFF+Secure/HttpOnly、明确SameSite/CSRF防护的会话cookie，长期token不暴露给浏览器JS；BFF到API使用有明确发行方的短期访问JWT。不能仅用反向代理IP或一个可伪造的user-id头作为身份。

认证提供者统一由身份适配层定义：企业SSO采用实际支持的OIDC授权码+PKCE等获准协议；本地账号仅用于经批准的独立认证/应急方案，禁止与SSO映射为多个可混用的质量身份。公司人员映射使用稳定ID，不以可改姓名/邮箱字符串当唯一授权标识。

JWT验证签名、算法白名单、iss/aud/sub/exp/nbf等实际合同声明，管理密钥轮换、会话撤销、停用/离职和失效范围；JWT通常是签名而非加密，不放敏感结果。JWT TTL不能替代实时撤权。关键命令检查PG中的账号/资质/会话版本，Redis不可用时不得默认放权；验证方需测撤销传播和令牌重放。

IdP与HBOS中承担认证的部分列为受控外部依赖。Portal不可访问时可直达LIMS；IdP故障不保证仍可新登录，连续性方案须批准、演练和追踪。Next Proxy只做访问体验优化，FastAPI对所有入口独立鉴权。

## SEC-02 细粒度权限

授权=角色动作许可 × 厂区/实验室/小组/项目或任务范围 × 资质有效性 × 业务状态 × 职责隔离。前端只能展示允许动作；API对直接调用、批量、导出、附件、统计和搜索同样校验。管理员不得默认代做检验/独立复核；双人确认必须两名不同有效身份，禁止同一人换角色完成。

采用deny-by-default。可使用PG RLS加强隔离，但若采用，须测试表主/超级用户绕过、连接池范围设置与清理；不能把RLS写进方案就宣称已安全。测试包括参数篡改、ID猜测、范围切换、过期资格、停用账号和对象权限变化。

## SEC-03 电子签名

每次受控签署明确显示记录版本、签署含义、需要确认的摘要并执行获QA批准的再鉴别/step-up；SSO登录、JWT、指纹图片或Modal点击本身都不是该记录的签名。非生物识别电子签名组件和连续受控会话的使用方式按适用21 CFR 11.200等评估，不能把一种实现写成全部场景的法定唯一方式。

签名关联稳定签署人、展示姓名、可信时间、含义、精确记录版本及鉴别事件。再鉴别成功后签发短时、单次、绑定actor/对象/版本/操作的签署授权，禁止重放或转移到其他记录；提交时再次检查版本和职责。密码/验证码不写审计或日志。签名、业务状态及质量审计原子提交；撤回/更正按新事件保留旧签名，不把签名删除。

审批后内容改变即失去对新内容的原批准，不得沿用旧签名。报告可读形式必须能看到相应签署姓名、时间和含义，报告归档与签署快照的来源一致；不能仅对含可变链接的页面截图签名。

## SEC-04 数据与运维

TLS、受控CORS、CSRF、CSP/安全头、输出编码、输入验证、上传大小/类型/恶意文件检查、最小权限和密钥管理需实现并测试；日志对token/密码/质量敏感字段脱敏。测试账号不可使用生产人员身份，公共CI不访问真实质量记录。

应用日志、质量审计、安全事件、数据库管理日志分别定义保留/权限和审阅。禁用应用账号删除受控记录；允许的作废/终止要保留事实与原因。数据库/存储管理员高权限行为单独审批、监测和复核，不能声称管理员绝不可能篡改。

第三方验证账号限验证环境、限定职责；不能因为是验证方就拥有生产root权限或代码合并权限。正式验证证据与电子批准存企业受控系统，GitHub保存不泄密的引用及完整性摘要。
